# AMR anti-slop specialist

Review the product as one coherent fan journey. React Native is the functional baseline; Swift is a separate prototype. Produce findings and acceptance gates only: this skill never authorizes scope expansion, provider activation, external writes, deployment, or deletion of existing work.

## Review method

1. Record revision, dirty paths, runtime versions, model ID, requested slice, and proof boundary. Read `AGENTS.md`, `CONTEXT.md`, `DESIGN.md`, owning specification, active work/bug context, relevant contracts, and tests. Classify each claim as implemented, accepted plan, recommendation, or unverified.
2. State the journey in one sentence and trace it end to end. Define observable acceptance cases (3–8), including a failure/retry and a stale/offline/permission case where applicable. Every user-visible state needs meaning, accessible status, action, and recovery: signed out, loading, success, empty, unavailable, denied, invalid, timeout, retry, cancel, stale, offline, expired, and terminal completion.
3. Trace every displayed number to server source, policy/version, unit, period, provenance, and authorization. Keep points, true activity, evidence scores, estimated fan/community travel impact, and approved Aston Martin metrics separate. Demo/fixture data must be labelled and excluded from real totals.
4. Review async boundaries for cancellation, cleanup, ownership/session isolation, idempotency, replay/conflict, timeout, and concurrent retries. Model output is untrusted classification/explanation; it cannot choose points, CO2, roles, permissions, or official claims.
5. Apply the evidence-backed checks in [research.md](references/research.md): status announcements without forced focus, target size, reduced-motion behavior, specific recovery copy, consistency with domain terms, and YAGNI. Do not call a choice slop merely because it is unfamiliar, minimal, gradient-based, or visually simple; cite the violated contract or observed usability consequence.
6. For emulator review, record platform/API, build command, test account/mode, exact steps, observed states, and artifact path. Separate emulator observations from Jest/API proof; never infer iOS, physical-device, background, provider, Azure, or production behavior.

## AMR release gates

- Photo activity: 1–5 canonical images, bounds, duplicate handling, cleanup, description validation, strict Luna output, explained bounded evidence score, timeout/failure, owner scope, same-key replay/conflict, deterministic server-owned reward, and no score-to-CO2 or client points multiplier.
- Missions: stable IDs, race-week/personalized source, timezone/expiry, enrollment/ownership, progress idempotency/concurrency, retry behavior, and clear official-programme attribution.
- ESG: separate personal, community, and official approved rows with unit/period/method/provenance; unavailable distinct from zero; pending/superseded/cross-profile reads tested; demo excluded.
- Quality: exact focused commands/results, assertion inspection, and explicit missing proof. Typecheck/lint or a screenshot alone cannot establish integration, accessibility, concurrency, performance, or device claims.
