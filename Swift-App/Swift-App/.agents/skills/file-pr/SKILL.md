# File PR

## AMR project rules

Read [AGENTS.md](../../../AGENTS.md) and [CONTRIBUTING.md](../../../CONTRIBUTING.md)
before PR work. They define local verification, focused scope, size labels,
review requests, evidence handling, monitoring and exact model attribution.
Invoking this skill alone does not authorize commits, pushes, PR creation,
comments or merging. Use the available T3 linking tools when working in T3 Code.

## Resolve the intent first

- If the user says to use this skill "against" an existing PR, provides a PR URL without an action verb, or otherwise asks to look at a PR, review it and report back. Inspect the diff, checks, reviews, and comments, but do not edit the PR, push code, or add comments.
- If the user explicitly asks to file, open, update, comment on, fix, or babysit a PR, perform only that requested mutation.
- When the request is genuinely ambiguous and the difference would cause a mutation, default to read-only review.

For a review, lead with actionable findings ordered by severity and cite the affected files or lines. Say clearly when no findings remain, and mention checks that are missing or could not be run.

Before filing a pull request, check whether a PR for this branch already exists. Review the diff against `origin/main` to ensure that its contents match the goal.

## How to Use

PR titles usually become commit messages, so follow the repository's title conventions. Look at recently merged PRs and Git history for examples. Prefer a concise, human-readable title that explains why the change matters.

BAD

> perf(server): negotiate permessage-deflate on the websocket

GOOD

> perf(server): cut websocket frame size by 70%+ with gzipping

Open the description using a simple explanation of the problem based on the user's original prompt, then briefly explain the solution. Do not lead with an ex implementation inventory.

BAD

> Removed implicit workspace carry-over from every "new thread" entry point (cmd / cmd+shift+o, sidebar v1/v2 buttons, command palette). New threads inherit only the project from context; branch, worktree, and env mode always come from the configured defaults. Deleted buildContextualThreadOptions,startNewThreadInProjectFromContext, and the v1 sidebar's seed-context machinery.

GOOD

> My "new worktree" default was ignored when starting new threads on existing worktrees. Super unintuitive. Now your preferences always apply.

Add a blurb to the end of a PR description or comment only when an agent authored that text or the underlying changes. Do not edit a human-authored PR merely because it lacks a model or harness signature.

GOOD

> Generated by [model name] through [harness name].
> Change authored by [model name] through [harness name].

If the user asks you to fix a PR, make the authorized code changes and report the result. Add a PR comment only when the user also asks for a comment or when commenting is explicitly part of the requested repository workflow.

Open a real PR rather than a draft so review actions can run. A dedicated `babysit-pr` skill is unavailable in this checkout. When the user asks to babysit a PR, use the available repository and PR tools to follow the existing monitoring loop directly: poll checks and reviews newer than the last push, verify and address valid findings, push authorized fixes, wait for reruns, and repeat until review bots and checks are green on the latest commit. Disclose the missing dedicated skill, but do not pause for permission when the requested monitoring remains possible with manual tools.
