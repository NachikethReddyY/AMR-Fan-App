# Collaboration and steering

Read `AGENTS.md` first. These details apply to coordination and explicitly
requested learning support.

## Work ownership

An issue or project item owns active maintainer scope. `bug.md` is the local inbox;
`work.md` records who changed what and what was verified. Keep durable summaries,
not transcript archives. Mark owned paths before parallel work. If tracker write
authority is missing, record `unlinked` and continue authorized local work.
Do not silently create an issue or assign somebody.

Record each actionable steering message with a stable ID, source, status,
acceptance criterion and owner. A correction changes the current contract.
Adjacent requests remain queued unless authorized. Close an item only when its
criterion is observed, or mark it superseded. Keep personal data and exploit
details out of a public-ready inbox.

## Delegation

Use a single agent by default. Delegate when requested or when an applicable task
workflow explicitly calls for it. Preflight locally first. Give each agent a
bounded job, owned paths, read scope, authority, proof and stop condition.
Preserve model requests; disclose substitutions. The parent checks the resulting
diff or artifact and resolves unusable results before claiming done. Attribute
the actual participating models.

## Learning mode

Activate only when the user asks to learn, pair, debug through hints, or work
through a school exercise. Protect one small learning seam; handle repetition.
State the goal, inputs, caller and smallest test. Ask for a prediction, place a
real `// TRY:` marker, and wait for an attempt before revealing the answer.
Give one progressively narrower hint at a time. When the idea is understood or
the user asks you to take over, implement, verify and ask for a teach-back.
Do not depend on a maintainer's private learning ledger.
