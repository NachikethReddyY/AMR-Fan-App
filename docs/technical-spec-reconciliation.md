## Adopted shared requirements

- Use route-provider candidates or labelled fixtures; never invent live routes from a ranking model. Preserve a deterministic ranking fallback when the model is unavailable.
- Compute emissions, points, balances, eligibility and totals in deterministic code. Use sourced, versioned country/mode factors and disclose the configured comparison baseline. Label route differences "estimated CO2e avoided", not offsets or measured carbon savings.
- Separate official team-reported facts, app-community estimates and personal activity. Require source, period, unit, calculation method and approval evidence for official values. Do not publish pending extraction as a fact.
- Retain the append-only point history, one-time awards and spends, server-verified account ownership, admin authorization and non-negative balances already specified. The new draft's ledger and audit requirements reinforce these invariants.
- Real location collection is required. Use explicit start and stop controls, scoped consent, sparse sampling, private paths, short raw-trace retention and a deletion policy. GPS route matching must describe confidence and cannot prove a bus or train ride by itself.
- Label synthetic journeys, rewards and programme fulfilment. Neither a tree attribution nor a point redemption establishes a new planting or carbon offset.

## Implementation status and feature breakdown

The committed repository has an Expo starter; separate local UI work adds four tabs. It has no route provider, tracking, auth, backend, points ledger, reward operations, ESG ingestion or admin interface. This interview updates the specification. The user's correction establishes one fan-submission feature and one ranking, with 500 points to submit, contributions from 10 and up to three selections total at admin session close. Optional tags may label content without creating different workflows or quotas. The final answers confirm the single-driver baseline, fastest-route time reference, difference-only GPS top-ups and personal/community lifetime totals. [Feature documents](features/README.md) now own the detailed rules and remaining technical/design prerequisites.

For later implementation, keep the fan app's interface with route planning and journey results small. Route-provider and location adapters should feed normalized candidates and evidence into deterministic calculation and settlement modules. The candidate-ranking module may use a model adapter only if it adds tested value; its deterministic fallback belongs behind the same interface. This preserves one place for route eligibility and point invariants without requiring the draft's proposed service-per-domain layout. These are design constraints, not a selected backend package structure.
